### 104 机器

在 104 机器上，将上述 3 个参数依次配置为 `32/32/16` 时，查询提升并不明显。

尝试增大物理内存，不过需要重启机器，放弃。

通过 `EXPLAIN ANALYZE` 进行性能分析发现，虽然配置中已经将并行进程数设置的足够的，但计划和实际运行的 Worker 数量还是很低(只有 2)。这和表大小有关，测试发现，表的记录数为 ~60W 条时，Worker=2；而当表的记录数为 ~200W 条时，Worker=4。

不过不论怎样，依赖系统启动 Worker 始终无法达到很低的延迟。

一种方法是可以通过修改表的存储参数达到启动指定 Worker 数量目的，如下:
```sql
    ALTER TABLE tbl_trade_order SET (parallel_workers = 8);
```
进行性能分析时，也确实开启了 8 个 Worker。

以下是对 200W 条记录在不同条件下的测试记录。

- 这里将配置参数定为: max_worker_processes/max_parallel_workers/max_parallel_workers_per_gather = 32/32/16，取 parallel_workers 作为变量测试。

- 2-16 对比: 延迟降低 48%

### 测试结论

- 在进行查询优化时，可以根据物理机环境(主要是 CPU 核心数)，对配置项 `max_worker_processes`、`max_parallel_workers`、`max_parallel_workers_per_gather` 进行合理设置。
- 配置完成并重启机器，还需要进行性能分析，确定 Worker 数量足够。如果查询仍延迟较高，可以设置每个表的存储参数 `parallel_workers` 并测试。
- 此外，如果内存充足的话，可以将 `shared_buffers` 和 `effective_cache_size` 调大并观察测试结果。
